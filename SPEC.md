## Stack Overview

| Layer | Technology | Why |
|---|---|---|
| Game engine | HTML Canvas (vanilla JS) | 60fps with 50+ agents requires direct canvas control — no React re-renders in the game loop |
| Frontend framework | React 18 + Vite 6 | UI shells only (start/end/pause screens) — game loop runs outside React |
| Styling | Tailwind CSS 4 | UI screens only — canvas styled directly |
| Backend | FastAPI (Python 3.11) | Standard Pi stack, serves both API and static frontend |

| Server | systemd service `hunter` | Type=simple, auto-restart, same pattern as all Pi services |

## Frontend Architecture

### The React / Canvas Boundary

This is the most important architectural decision in the codebase.

**React owns:** Start screen, end screen, pause overlay, HUD (score + timer),
minimap. Anything that is UI, not game.

**Canvas owns:** The entire game simulation — fish positions, shark position,
particle effects, world rendering, camera transform. The canvas element is
rendered once by React and then handed off. React never touches it again
during gameplay.

The game loop runs in `useGameLoop.js` via `requestAnimationFrame`. It reads
input from refs (not state), updates simulation, and draws to canvas — all
without triggering React re-renders. Score and timer are written to refs
during the loop and synced to React state only at meaningful intervals
(every second for timer, on each catch for score). This keeps the UI
responsive without killing frame rate.

### PWA (Session 21)

Hunter is a genuine installable PWA. Manifest and service worker are both
generated by `vite-plugin-pwa` (`generateSW` mode), and nothing in the repo
hand-writes either. `registerType: 'autoUpdate'` plus the plugin's default
`injectRegister` mean the build injects its own registration script into
`index.html`; `main.jsx` is untouched.

**Manifest** (`display: 'standalone'`, `theme_color`/`background_color:
'#0a1628'`, `start_url: '/'`):

- `orientation: 'any'`, deliberately **not** `'landscape'`. Manifest
  orientation applies to the whole installed app: start screen, settings,
  leaderboard, tutorial, not just an in-progress round. Gameplay already
  locks to landscape imperatively via `screen.orientation.lock()` in
  `useFullscreen.js`, scoped to only while playing. A manifest-level
  `'landscape'` lock would force landscape on every other screen too, which
  the app deliberately does not do (StartScreen has a portrait-compatible
  compact layout; RotationToast nudges rather than blocks).
- Icons: `icon-192.png` (`purpose: 'any'`) and `icon-512.png` (`purpose: 'any
  maskable'`).

**Caching strategy** (Workbox `runtimeCaching`, all declarative, no
hand-written service worker code):

| Route | Strategy | Why |
|---|---|---|
| Navigation requests (`index.html`) | NetworkFirst, `hunter-shell` cache | Vite content-hashes `/assets/*`, but `index.html`'s URL never changes across deploys. A cache-first (or default-precached) `index.html` would strand every installed user on whatever build they first installed, with no recovery short of clearing site data |
| Hashed JS/CSS + icons + manifest | Precached (Workbox `globPatterns`) | Content-hashed filenames make this safe: a new deploy gets new filenames, so precaching can't serve stale code |
| `public/audio/*.mp3` (4 files, ~184KB) | CacheFirst + `rangeRequests: true`, `hunter-audio` cache | See below |
| `/api/*` | NetworkOnly, always | A stale cached leaderboard response isn't just cosmetic: `qualifies()` reads the last entry's score as the live 10th-place cutoff, so a stale response can offer submit for a score that no longer ranks, or hide it for one that does |

`index.html` is deliberately **excluded** from the default precache
(`globPatterns` has no `html` extension), and `navigateFallback: null` is set
explicitly. Without that, `vite-plugin-pwa` defaults to registering its own
`NavigationRoute` bound to the precache ahead of any custom `runtimeCaching`
rules, silently defeating the NetworkFirst rule above even though
`index.html` was never actually precached. This was caught by inspecting the
generated `sw.js`, not by assumption, and is worth re-checking after any
`vite-plugin-pwa` upgrade.

**Audio and the Range-request gotcha:** Workbox's default precache route has
no support for HTTP Range requests, and Chrome's media pipeline can issue a
byte-range `GET` for `<audio>` playback even on small files. A cached
response served as a plain `200` against a Range request can fail, and the
failure mode is silent audio, only in the installed app, easy to miss in
normal browser-tab testing. The four MP3s are therefore **not** in the
default precache; they're routed through a dedicated `CacheFirst` entry with
`rangeRequests: true` (the declarative Workbox shortcut for
`workbox-range-requests`). Trade-off: the ambient loop still warms almost
immediately (it's preloaded on mount by `useSound.js`), but the three
one-shot SFX only cache on first trigger, not at install time.

### Offline Behavior (Session 21/22)

`EndScreen.jsx` distinguishes **offline** from **the fetch merely failed**
via `navigator.onLine`, listening for `online`/`offline` events for the
lifetime of the screen.

- **Offline:** submission is blocked outright, with no name input, no POST
  attempted, just a plain message instead ("You're offline, scores can't be
  submitted right now"). This holds regardless of personal-best status.
  Deliberate design decision, not an oversight: `qualifies()` needs a live
  board to compare the score against the current 10th place, so offline
  there is no way to know whether a score would even rank. Queuing the
  submission for later was considered and rejected, since it would mean
  either prompting for a name on every offline round (most of which would
  never actually qualify) or deferring the qualification check to flush time
  (submitting something the player was never shown as qualifying). Both are
  worse than telling the player plainly that submission isn't available
  right now.
- **Online but the fetch failed:** keeps the older personal-best fallback.
  A transient server hiccup is not the same as submission being
  fundamentally impossible.
- **The personal-best flourish always shows**, offline or not. It's
  computed purely from `localStorage`, so an offline round is never a dead
  end for the player.
- On reconnect, the preview fetch is retried automatically. A request-id
  guard in `loadPreview()` (Session 22 Bug 2) discards a stale, late-arriving
  response from an earlier offline attempt if a newer request has already
  resolved. Without it, a real-device race (the offline request can take a
  long time to actually reject, not fail instantly) could let a late
  rejection overwrite a just-succeeded reconnect fetch, which read as
  "Couldn't load scores" persisting despite a healthy network.

## API Contracts

### GET /api/leaderboard?difficulty=easy|normal|hardcore&platform=desktop|mobile

Returns the top 10 scores **for that difficulty + platform**, ordered by score
descending. Each difficulty board is split by platform (desktop play is harder,
so scores aren't comparable) — 6 boards total.

- `difficulty` query param **required** — `easy`, `normal`, or `hardcore`.
- `platform` query param **required** — `desktop` or `mobile`.
- Missing or invalid either param → **400**.
- Empty array if no entries for that combination.

**Response 200:**
```json
[
  {
    "id": 1,
    "name": "Job",
    "score": 23,
    "theme": "ocean",
    "difficulty": "easy",
    "platform": "desktop",
    "created_at": "2026-06-28T10:30:00"
  }
]
```

Always returns an array. Max 10 items.

---

### POST /api/leaderboard

Submit an opt-in leaderboard entry. Only called when player explicitly
chooses to add their score.

**Request body:**
```json
{
  "name": "Job",
  "score": 23,
  "theme": "ocean",
  "difficulty": "easy",
  "platform": "desktop"
}
```

**Validation:**
- `name`: untrusted string. Cleaned server-side (`clean_name`): Unicode
  normalized (NFC); control chars, bidi overrides (e.g. U+202E), and
  zero-width/BOM chars stripped; internal whitespace collapsed; trimmed. Must be
  1–20 characters **after cleaning** (a 200-char raw ceiling rejects oversized
  payloads first). Blank/whitespace/invisible-only → 422.
- `score`: integer, `ge=0`, and capped **per difficulty** at that mode's fish
  count (Session 18): Easy ≤70, Normal ≤60, Hardcore ≤50 — a score above a
  mode's own fish count is impossible. Enforced by a model validator that runs
  after `difficulty` is parsed/normalized, so it applies regardless of field
  order in the request body.
- `theme`: enum — `"ocean"` only in v1
- `difficulty`: enum — `easy` / `normal` / `hardcore` (defaults to `normal`)
- `platform`: enum — `desktop` / `mobile`, **required** (invalid → 422)

**Response 201:**
```json
{ "status": "added" }
```

**Response 422:** Pydantic validation failure (malformed/oversized/unsafe input).

**Security posture (public, unauthenticated endpoint):**
- **SQL injection:** not possible — every query is parameterized (`?` placeholders).
- **XSS:** the API stores the raw (cleaned) name; the React client escapes on
  render (no `dangerouslySetInnerHTML`), so a name like `<b>hi</b>` is shown as
  literal text. Server-side cleaning is defense-in-depth, not the XSS boundary.
- **Rate limiting:** none in-app. The service sits behind the Cloudflare Tunnel,
  so `request.client.host` is the tunnel (all users share it) — an in-app per-IP
  limiter would be ineffective/incorrect. **Recommended:** a Cloudflare WAF
  rate-limiting rule on `POST /api/leaderboard` at the edge (correct client IP,
  no app changes). Submits are opt-in and capped at 10 per board, so abuse impact
  is low, but edge rate limiting is the right guard if it becomes a problem.

Covered by the backend test suite (`backend/tests/`, 40 tests) — see Testing below.

## Data Model

### leaderboard table

```sql
CREATE TABLE IF NOT EXISTS leaderboard (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT    NOT NULL,
    score       INTEGER NOT NULL,
    theme       TEXT    NOT NULL DEFAULT 'ocean',
    difficulty  TEXT    NOT NULL DEFAULT 'normal',
    platform    TEXT    NOT NULL,             -- 'desktop' | 'mobile' (Session 11)
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Single table. No migrations framework — schema created on startup if not
exists. `init_db()` performs a one-time reset: if a pre-`platform` table is
found it is dropped and recreated (wiping old scores), then left untouched on
later startups. Leaderboard data is not critical, so drop-and-recreate on schema
change is acceptable.

## Client-Side Storage

| Key | Type | Value | When set |
|---|---|---|---|
| `hunter_pb_easy` | localStorage | integer | PB for Easy mode |
| `hunter_pb_normal` | localStorage | integer | PB for Normal mode |
| `hunter_pb_hardcore` | localStorage | integer | PB for Hardcore mode |
| `hunter_difficulty` | localStorage | `easy` / `normal` / `hardcore` | On difficulty select |
| `hunter_tutorial_seen` | localStorage | `"true"` | After tutorial completed or skipped |
| `hunter_setting_audio` | localStorage | `"true"` / `"false"` | Audio on/off toggle (default ON). Replaces the legacy `hunter_mute` (migrated once if a mute preference existed) |
| `hunter_rotation_toast_shown` | sessionStorage | `"true"` | After the portrait toast is shown (once per session) |

The old global `hunter_pb` key is retired (ignored if present). No cookies.
`sessionStorage` is used only for the once-per-session rotation toast. No IndexedDB.

The `hunter_setting_audio` preference is owned by a single source of truth —
`src/settings.js` — which caches it in memory and mirrors to localStorage. Every
consumer (settings panel, the audio hook, the start/pause toggles) reads the
**same live value** through `isAudioOn()`, so a toggle takes effect immediately
and can never go stale. (The glow-on-fleeing-prey setting was removed in
Session 15 — glow is now permanent, applied unconditionally by the renderer.)

### Testing (backend)

Backend API tests live in `backend/tests/` (pytest + FastAPI TestClient). They
cover the untrusted leaderboard **name-entry** path — acceptance/normalization,
rejection (blank, over-length, invisible-only, oversized), sanitization (control
chars, bidi overrides, zero-width, NUL), injection/XSS neutralization — plus
score/enum validation (including the per-difficulty score ceiling), GET
requirements (including case-insensitive difficulty/platform params), board
isolation, health, empty/tied/exact-boundary boards, field defaults, the
one-time destructive schema migration (`init_db()`), and the
StaticFiles-mounted-last route ordering invariant.

```bash
cd backend
.venv/bin/pip install -r requirements-dev.txt   # pytest + httpx (first run only)
.venv/bin/python -m pytest -q                    # 40 tests
```

Tests run against a throwaway DB via `HUNTER_DB_PATH` (and, for the
StaticFiles ordering test, a throwaway fixture dir via `HUNTER_DIST_DIR`), so
`leaderboard.db` and the real `frontend/dist/` are never touched.
`requirements-dev.txt` is dev-only — not installed in production.

### Testing (frontend)

Frontend tests live alongside the source they cover (`*.test.js` /
`*.test.jsx`), run with Vitest + jsdom + React Testing Library.

```bash
cd frontend
npm run test        # vitest run
npm run test:watch  # vitest (watch mode)
```

**On `main`, this currently reports 211 tests, 208 passing, 3 failing.**
That is expected, not a broken build. The 3 failures are deliberate,
fail-first regression markers for two known, already-diagnosed bugs
scheduled for later phases (see ROADMAP.md):

- `useGameLoop.test.js`: asserts `dtSeconds` gets clamped after a long
  frame stall. It isn't yet, so a backgrounded/interrupted round currently
  gets charged the full wall-clock gap against its timer in a single frame.
- `useInput.test.js` (×2): assert the mobile joystick's activation zone
  clears Android's edge-gesture exclusion strip by a safe margin. It
  currently sits closer to the edge than that.

Each failing test's assertion documents the *intended* behavior. The
measured value in the failure output is the actual, current, unfixed
behavior. Do not "fix" these tests to make the suite green. Fix the
underlying code instead, at which point the tests start passing on their
own.
